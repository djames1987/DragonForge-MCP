# C-001A / C-003A — Client identity, owner IPC, worker IPC
Status: detailed delegated design, Phase 0 documentation only. DEC-002/003, C-001/003/006, T-003/010/013/020.

## Clients and credential semantics
Owner authenticates using Windows named-pipe peer token; server generates 256-bit CSPRNG secret (BCryptGenRandom, system-preferred RNG) and independent 128-bit random key_id. Credential is never sent through MCP, CLI argv, audit, JSON logs or worker environment. Store keyed HMAC-SHA256 verifier using 256-bit pepper protected by DPAPI with gateway-private ACL. Compare with constant-time equality. Challenge input domain separation: UTF-8 'DFMCP-CRED-V1\0' || instance_uuid || client_uuid || key_id || 32 credential bytes. Credential supplied on HTTP only in Authorization: Bearer <base64url> over 127.0.0.1 with Host and Origin checks; local traffic is not intrinsically confidential from same-user malware. Reject multiple Authorization headers, alternate schemes, unknown key, malformed base64url, expired/revoked client, or store failure without leaking which check failed. Credential key_id may be transport metadata but is not authentication. Credential issuance happens only through protected Windows Credential Manager/DPAPI one-time enrollment delivery to an owner-selected host adapter; no stdout bearer tokens.

Enrolled client has separate DISCOVER and INVOKE grants. No host-provided _meta/clientInfo display name or STDIO process parent determines principal. STDIO bridge provisions one specific client identity from its protected OS store and forwards over local authenticated channel; deny bridge without provisioned identity. Credential default expires 90 days, overlap rotation ≤24h explicitly requested, revocation immediate at next grant recheck including pre-spawn; queued work cancelled, running side effects remain uncertain. Clock rollback and restore require monotonic epoch/recovery check.

## Owner administrative pipe envelope
Envelope framing: 4-byte big-endian unsigned length then strict UTF-8 I-JSON object, max 1 MiB, depth ≤32, duplicate keys rejected. Fields required: protocol='dfmcp.admin', version=1, request_id=UUID, operation=canonical CLI command ID, args=typed object, expected_revision (null for read), deadline_ms 100..30000. Only the authenticated peer token supplies owner identity, not args. Reply: request_id, ok boolean, data object on success or error {code,message} on failure, authority_epoch and audit correlation. Unsupported version, malformed framing, nonce replay or wrong SID fail before dispatch. Server rejects all operator actions while recovery gate is locked except documented recovery-safe operations.

## Worker peer protocol
C-003 existing framing remains a 4-byte big-endian uint32 length and strict UTF-8 JSON, max 4194304 bytes, depth 32. Per connection random channel_id bound out-of-band to the exact OS-verified AppContainer SID, launched worker token and single inherited launch channel; a message cannot establish authority by possessing channel_id. No challenge-proven bearer login is required at the wire layer. If later defense-in-depth adds a challenge proof, it must be a versioned schema extension and cannot bypass OS peer verification. **Important:** challenge proof alone is not identity; both verified AppContainer peer SID and unforgeable handle provenance required. Connection states CREATED->OS_VERIFIED->HELLO->READY->CLOSED. One in-flight invocation/channel, strict id matching; result only once, no unsolicited request messages.
Version 1 messages: hello {protocol,version,kind,channel_id,worker_kind,pid}; ready {protocol,version,kind,channel_id}; invoke {protocol,version,kind,channel_id,invocation_id,tool_id,tool_version,package_sha256,deadline_budget_ms,input,capability_handles}; result {protocol,version,kind,channel_id,invocation_id,status,output|error_code}; cancel {protocol,version,kind,channel_id,invocation_id,reason}. Unknown security-significant fields reject. Never include client credential, owner SID token, DB path or approval material.

## Capability handle
Normative descriptor is the C-003A object with handle_id UUIDv4, kind, scope_hash, expires_monotonic_ms, policy_epoch and invocation_id, no secret-bearing token or raw OS handle included. The gateway keeps a private mapping from handle_id to {invocation ID, worker OS SID, exact capability, stable resource identity, policy epoch, expiry}; it checks the verified worker token, grant, policy epoch, package digest and scope every use. Consume each descriptor atomically for one broker operation; revoked if client/grant changes. Capability handles are never broad bearer credentials and broker must also validate OS peer identity and current grant. Reparse/redirect checked at use, not merely token issuance. Worker cannot mint/extend scopes.

## Races and invariants
Admission + one-time approval consumption + audit committed in single SQLite transaction; before worker launch recheck credential/client/grant/version/digest/revocation epoch. Concurrent rotation: old key valid only if explicitly within unexpired overlap and not revoked. Cancellation after an external side effect => UNKNOWN_EFFECT if outcome cannot be proven. On worker crash no automatic retry for non-idempotent tools; known keyed retries require same canonical argument hash. IPC authentication failure never results in fallback to ordinary subprocess. Planned fixtures: ID-01..08 credentials, STDIO spoofing and client cross-access; PIPE-01..09 OS identity, framing, replay, forged channel, oversize, expired capability, package change and crash. Not executed.

## Cross-contract precedence reconciliation — 2026-10-25
The worker message field sets, timing, parser limits, capability descriptor serialization and broker token behavior are governed by **C-003A section 7 of `worker-ipc-wire.md`**, superseding this document's earlier candidate examples. No implicit runtime challenge-proofs, 192-bit bearer-token handles or alternate result fields are allowed without a versioned owner-approved change. Admin IPC's `deadline_ms` is 100..30000 and the machine-readable request and response shape follows C-007F registry; any earlier 1..30000 prose is superseded. Enrolled MCP client credentials remain a separate C-001 security boundary; the worker is never granted a client bearer secret.
