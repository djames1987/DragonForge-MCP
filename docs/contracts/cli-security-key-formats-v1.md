# C-007C — Administrative CLI security and key formats
Status: proposed normative Phase 0 contract; C-007A command catalog and C-007B/JSON Schema registry apply. **No command implementation or key handling has been tested.**

## Administrative request validation
A CLI command is untrusted until the gateway verifies the actual Windows named-pipe peer token, its owner SID, logon session and confirmation context. `args.owner_sid`, `args.approved`, `--yes`, interactive script input, MCP metadata and worker attestations cannot confer owner authority. Request frames: four-byte big-endian length + UTF-8 strict I-JSON, <=1 MiB, depth <=32, duplicate keys rejected, `protocol="dfmcp.admin"`, `version=1`, random UUID request_id and per-operation `args`. Unknown command/field => SCHEMA_INVALID before access. The published `cli-command-schema-registry-v1.json` enumerates the 54 outer operation envelopes; JSON Schema does not itself verify OS user identity, file system semantics, ownership or interactive consent.

## Owner confirmation
Sensitive CLI-022 trust, CLI-026 remove, CLI-035/036 approval, CLI-044 migration, CLI-045 recovery, CLI-049 restore, CLI-050/051 key transfer, CLI-054 purging, CLI-016 client recovery require owner-authenticated interactive challenge. Gateway generates 256-bit nonce, binds `{operation,request_id,principal owner SID,target IDs,tool package digest,arguments SHA256,policy epoch,expiry}`, displays immutable human-readable action; expires in 120s, one-use state in gateway SQLite; terminal deny on disconnect, expiry, revision change or mismatch. The trusted CLI must display target principal/scope without secrets and require explicit typed confirmation of a short nonce suffix (not a client-provided approval token). Trusting a tool is never permission to execute it; grant and enable remain independent. Noninteractive stdin/JSON mode cannot bypass confirmation; `--json` is output formatting, never proof of approval. Owner-approved automation of sensitive operations is out of initial release scope.

## Secret delivery state machine
`ISSUANCE_REQUESTED -> ISSUED_PENDING_DELIVERY -> DELIVERED` or `REVOKED_DELIVERY_FAILURE`. Gateway generates 32 random bytes using BCryptGenRandom system RNG and stores HMAC-SHA256 verifier under separately DPAPI-protected pepper, never plaintext in DB. Owner-authenticated local adapter uses Windows Credential Manager entry `DragonForgeMCP/<instance>/<client>/<credential UUID>` under target owner Windows logon. Only that adapter account receives protected credential via the authenticated administrative channel; no command argv/env/stdout/JSON result may contain bearer bytes. Deliver only a metadata `delivery_reference`; if protected write or readback fails, audit and revoke credential atomically before any call may authenticate with it. Credential Manager is not a sandbox against malicious code already running as the same Windows user. The owner must verify local process integrity separately.
Rotation produces a fresh 256-bit credential, max 24h deliberate overlap, old revoked immediately on explicit revoke or overlap expiry. Clock rollback or DB/checkpoint mismatch denies authentication.

## Encrypted backup format DFMCP-BACKUP-1
On-disk file is byte sequence:
- 8-byte ASCII magic `DFMCPB01`; 4-byte big-endian header length N (0<N<=65536); N strict canonical I-JSON bytes; ciphertext; 16-byte AES-GCM authentication tag.
- Header properties exactly: `version:1`, `instance_id:uuid`, `backup_id:uuid`, `schema_version:uint`, `recovery_generation:uint`, `authority_epoch:uint`, `nonce:base64url(12 bytes)`, `ciphertext_sha256:64 lowercase hex`, `key_slot_id:uuid`, `kdf:"ARGON2ID-1"` for exported recovery envelope or `kdf:"DPAPI-LOCAL-1"` for local backup, `created_at:UTC timestamp`. Header authenticated as AES-GCM additional data (AAD) in exact bytes. Compare ciphertext SHA before decrypt as a corruption fast path; GCM tag verification is authoritative, SHA alone is not authenticity.
- Fresh 32-byte DEK generated for each backup; AES-256-GCM nonce fresh random 12 bytes per backup and unique with that DEK. A DPAPI-protected key slot stores DEK locally under owner profile; a separate owner export rewraps the DEK rather than reusing passphrase as backup encryption key.
- Exported recovery envelope: separate file with 8-byte magic `DFMCPK01`, 4-byte length + canonical I-JSON header, 12-byte nonce, AES-256-GCM ciphertext of `{instance UUID, key-slot UUID, DEK 32 bytes}`, 16-byte tag. Derived wrapping key via Argon2id version 0x13 with memory 65536 KiB, iterations 3, lanes 1, 16-byte random salt, 32-byte output key; minimum passphrase policy 16 Unicode code points after NFC normalization, owner interactive entry only, no argv/env. These are delegated concrete defaults, and memory feasibility must be qualified on reference hardware; if unsupported, fail closed, not downgrade.
- Export destination must be new (CREATE_NEW), private owner ACL only, non-reparse, no existing hardlink, flushed and verified before claiming completion. Import rejects unknown version, KDF params outside bounded cost, failed AEAD, foreign instance, stale recovery generation and unsupported platform; never write a partial key into active store. Zeroize temporary plaintext buffers on a best-effort basis, acknowledge swapping/dump risk.
- `export-key` output JSON gives only slot UUID, destination path and envelope digest. Never include passphrase, plaintext key or verifier. Misplaced/lost export file is not recoverable by guessing keys.

## Common failure response constraints
Structured error codes: SCHEMA_INVALID (exit 2), NOT_FOUND (3), AUTH_INVALID/ACCESS_DENIED/APPROVAL_INVALID (4), CONFLICT (5), STORE_UNAVAILABLE (6), INTERNAL_ERROR/ISOLATION_UNAVAILABLE (7), RECOVERY_REQUIRED (8). Error messages contain no secret, package execution args, named-pipe internal handle, or raw OS token. Every response includes a UUID correlation_id; failed sensitive requests produce redacted audit evidence if storage available; inaccessible audit locks mutations. Do not automatically retry non-idempotent requests.
